# 武汉旅行 Notebook 数据模式与设计讨论稿

这是一份给下一位 Claude agent 的项目上下文。用户想做一个可部署到 Vercel 的武汉旅行 Notebook，把武汉地图、各街区的策划章节和自己的 Daily Plan 连起来。主要使用场景是旅行前选片区和排日程，以及在武汉用手机快速决定接下来去哪、到了点什么或玩什么。现阶段先讨论产品和数据设计，Citywalk 的站点和顺序等用户一起讨论后再定。

## 页面与主要操作

下面的 URL、控件和操作顺序是上轮讨论提出的方案。用户明确需要武汉地图、各街区的 Citywalk 策划和一个独立的 Daily Plan 页面。

| 页面 | 建议 URL | 要帮用户做的决定与操作 |
| --- | --- | --- |
| 武汉地图 | `/` | 全城有哪些值得去的街区，它们相距大概有多远。点街区看代表地点和简短介绍，再进入对应章节。 |
| 街区 Chapter | `/chapters/:slug` | 这一片吃什么、点什么、玩什么。先看精选 Highlight，再按吃喝、逛店、看建筑等筛选，或搜索店名和资料里已有的菜名。街区地图显示可定位的地点，预留 Citywalk 区域。 |
| Daily Plan | `/plan` | 今天去哪几站，按什么顺序走。按日期组织早上、午餐、下午、晚上。未定日期的地点可以先进「待安排」，也可以从卡片直接加到选定日期。当天支持调整顺序、换备选、查看地图，以及在位置准确时打开高德。 |

用户说希望整体「轮动、直白、方便做旅游决策」。目前将「轮动」理解为地图、列表和行程之间的联动。点地图标记时同步高亮列表里的地点，点列表时定位到同一个标记。手机上可以从底部打开地点详情，读完即可加到某天。用户已经标为 Highlight 的地点应当在列表里容易找到；置顶、筛选或标记的具体形式待讨论。

## 街区章节与地点详情

章节采用统一的 HTML 页面结构，方便按同一种方式添加街区。先交代这片区值得去的理由和精选点，再让用户筛选具体地点。Citywalk 可以先显示「路线待定」，等站点和顺序确认后再画步行路线。参考帖可以作为讨论素材。

地点详情的首屏建议直接回答三个问题。

1. **为什么去。** 一句话说明值得专程去还是适合顺路停留，并注明该判断的依据。
2. **到那点什么或做什么。** 餐饮显示有资料依据的推荐菜、饮品或食物，店铺和景点给出具体可做的事。标明建议来自用户、帖子作者或图片所见。资料不足时，保留待核实状态。
3. **要放在哪天。** 提供加入某天或暂存「待安排」的入口。有准确定位的地点可以打开地图。

截图、原文、来源、地址、营业时间与待核实事项放在下面展开。用户后续可以继续通过知识库截图或文字提供内容，店铺名称和原文用词保留。例如「香钿 DIAN」的来源仅支持「图片里有华夫和中式菜品」。可以显示这条观察，具体点单推荐和分店地址仍待核实。[香钿 DIAN 资料](../data/知识库/地点/香钿%20DIAN/资料.json)

## 仓库现有数据

知识库使用 UTF-8 JSON 和中文字段。`null` 表示未知或未填写，空数组表示目前没有收录。提取或审核仍在进行的资料要保留相应状态。[知识库说明](../data/知识库/README.md)

| 资料 | 仓库位置 | 现有结构与状态 |
| --- | --- | --- |
| 目的地 | `data/知识库/目的地/名称/资料.json` | 街区、商圈或景区。含名称、类型、简介、关联地点、来源和待核实事项。一个地点可以关联多个目的地，具体区域或分店未明时先保留待核实。 |
| 地点 | `data/知识库/地点/名称/资料.json` | 店铺、地标或景点。含名称、类别、简介、所属目的地、地址、坐标、开放时间、建议停留分钟、图片、来源和待核实事项。地址可记录内容、状态、来源与查询日期。 |
| 原始来源 | `data/xiaohongshu/posts.jsonl` | 每条小红书帖子有 `post_id` 和提取状态。地点的 `来源` 记录平台、帖子编号和具体依据，可以回查原文及审核进度。 |
| 路线与清单 | `data/知识库/路线/` | 当前有小红书作者路线和店铺清单，保存来源给出的条目顺序与待核实信息。其中距离、实际通行情况、分店位置或顺路程度可能尚待确认。 |
| 候选与待识别 | `data/知识库/发现与待补充/`、`data/知识库/待识别-餐饮.json` | 收录地图候选、待补资料和地点身份未确定的线索。纳入精选和确认分店需要各自的依据。 |
| 每日行程模板 | `data/知识库/行程/每日行程模板.json` | 当前是草稿模板，含日期、出发地点、交通偏好、节奏、预算和安排。安排可引用目的地与地点，并记录时间、停留和下一段交通。 |

## 页面需要补充的数据

以下是讨论用的字段建议，可以先用现有资料检验。正式字段名和存放位置等方案确认后再决定。

| 记录 | 建议包含 |
| --- | --- |
| 街区章节 | 可用于 URL 的 `slug`、关联目的地、简短导览、精选地点及顺序、可选的 Citywalk 路线引用。 |
| 地点精选与推荐 | 地点引用、Highlight 标记、推荐理由、可搜索的菜名或活动、每一条建议的来源与核实状态。店铺基础资料仍由同一份地点记录维护。 |
| Citywalk | 所属章节、路线状态、按顺序排列的地点引用、途经点或步行线路。实际距离与耗时有依据时再填写。来源路线与用户选定的路线可以分别引用。 |
| Daily Plan | 日期或「待安排」、一天中的时段、地点引用、排序、可选备注和备选地点。当天调整顺序后，地图按同一天的行程更新。 |

开始做页面时可以给地点设稳定引用，避免改店名或切换显示语言时影响地图选中和已存行程。同名分店应先核对身份。地图标记和导航以确认过的分店位置为准。地址、营业时间、价格、入口与预约这类会变的内容保留来源、查询日期与核实状态。用户给的截图或文字保留对应来源，区分图片所见、帖子作者评价、用户选择和独立核实。[知识库的来源与地图规则](../data/知识库/README.md)

## HTML 与 Vercel 方案

讨论中的方案是用 Vite 生成多页静态站，从仓库 JSON 读取章节和地点。首页、各街区和 Daily Plan 各有独立 URL，直接打开或刷新也能进入对应页面。筛选、详情弹窗和行程排序由浏览器处理。高德地图可以提供地图标点、步行线路显示和打开地图的入口。首版可把 Daily Plan 保存在当前浏览器。如果用户需要电脑和手机自动同步，再讨论共享存储和访问方式。[Vercel 的 Vite 部署文档](https://vercel.com/docs/frameworks/frontend/vite) · [高德地图 JS API](https://lbs.amap.com/api/javascript-api-v2/summary)

## 和用户继续讨论

1. **确认「我的 popuo」的意思。** 上轮暂按点击店铺后打开的详情弹窗理解。另一种可能是用户收藏的 pop-up 快闪店或活动。如果指快闪，活动日期和地点将直接影响能否加到某天。
2. **用一个章节定下信息优先级。** 建议拿黎黄陂路试聊。已有巴公房子、洞庭81、兰陵路及一条小红书作者路线，可以讨论哪些应该在首屏当 Highlight、哪些是备选、每个点还缺什么。具体站点和步行顺序由用户一起确认。[黎黄陂路街区资料](../data/知识库/目的地/黎黄陂路历史街区/资料.json) · [来源路线](../data/知识库/路线/黎黄陂路街区来源路线.json)
3. **确认 Daily Plan 是否需要跨设备。** 如果用户打算在电脑上排、到武汉后用手机接着改，优先讨论同步。如果主要在一台设备上用，可以先验证浏览器保存是否满足需求。

可以先请用户挑一个街区，并拿一两条已有截图或文字一起走一遍「看到 Highlight → 决定点什么或玩什么 → 加进某天」。确定这个流程后再展开页面设计和实现。
